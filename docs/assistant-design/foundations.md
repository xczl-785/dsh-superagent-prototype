# 已对齐的基础与信息边界

本文件承载已对齐的设计基础。尚未确定的交互和存储实现见[提案](interaction-proposals.md)。

## 用户目标与现有条件

用户安装插件后感到不好用，希望通过个人 fork 调整。沟通发现，现有系统对派任务、执行、收结果有明确支持，但用户还需要理解工程、交流灵感、探索方向和梳理问题的协作能力。这个过程不应要求用户一开始就掌握工程细节或提供完整实施任务；具体目标、能力与责任边界在 [design-focus.md](design-focus.md) 维护。

设计必须考虑多个 feature 并行。代码、需求和文档随 feature 快速迭代；资产还会经过整理、提炼、归纳、移动、删减。已有项目认知可能过时，不能把旧对话内容直接当作当前工程事实。

用户已明确 docs-workflow 是准备使用的资产盘点、整理和维护机制，并提供 RouteLedger 作为推进状态基础。具体接法不在当前范围；设计接受资产会持续变化这一条件，不另行设计一套替代治理系统。

用户要求按问题和角度逐步拆开讨论，避免在一个问题尚未对齐时同时铺开交互、记忆、资产治理和实现细节。

## 项目资产与助理记忆

两者承载不同信息，可以同时存在。不能把它们视为保存同一套工程知识的竞争方案。

| 内容 | 归属与用途 |
| --- | --- |
| 代码、架构、需求、有效决定、约束、工作状态、必要理由和下一步 | 项目资产，供 agent 按任务获取并建立工程认知 |
| 稳定协作偏好、沟通习惯、值得跨会话延续的交流背景 | 助理记忆，改善协作连续性，不承担项目事实的权威来源 |
| 尚未形成有效决定的发散讨论 | 可先留在对话；是否提炼为资产或记忆，取决于后续用途 |

用户明确偏好把项目内容沉淀到资产中，并按 `agent-docs` 面向冷启动 agent 记录。其关键要求在这里落实为：有效结论有明确归属，必要上下文可检查，区分事实、决定、提案和未知，内容变化时更新原归属而非不断追加旧结论。

助理记忆可以与某个项目有关，但不能在项目资产之外维护另一套项目现状。例如：

- “这个 feature 不做自动提交”是项目约束，应进入项目资产。
- “用户通常希望先拆问题，再比较方案”是协作偏好，可以跨会话记忆；适用范围仍需明确。
- “项目当前采用方案 A”应从当前项目资产确认。
- “曾考虑过个人助理方向，目前未定”可以作为交流背景，但不能作为已接受需求或实施授权。
- “为什么放弃方案 A”若影响后续工程判断，应随项目决定保存，不能只留在助理记忆里。

来源：用户指出“项目的内容我更喜欢沉淀下去，并以 agent-docs 的形式去记录”“两种模式，需要记录的内容其实完全不一样”；后续确认项目资产由自己的方式维护、助理记忆独立保存。

## 助理记忆的维护归属

基本操作、获取使用闭环、用户可纠正性以及可选回顾提炼 skill 在 [assistant-memory.md](assistant-memory.md) 维护。本文件只维护两类内容的分界、项目资产沉淀/获取与原始对话兜底。

## 项目内容何时沉淀

### 默认意识、主动沉淀与可用入口

agent 默认知道项目资产与助理记忆的不同归属，主动识别值得保留的信息并在适用时机沉淀，不依赖用户每次明确要求“记一下”。

项目资产的判断准则：缺少该信息会使接手者误解项目、重复决策或做错工作。包含必要的目标、需求、约束、决定及理由、工作状态和未决问题，不限于最终结论。

助理记忆的判断准则：跨对话仍适用、能改善个人协作，且不需要作为项目事实共同维护。未落文档的交流不自动归入助理记忆：影响项目后续判断的进入资产；本段交流的位置和细节可留在对话及接续上下文；个人协作信息才提炼为助理记忆。原记录被保存不等于其中每条内容都成为有效记忆。

当前设计方向为：默认指令提供归属、责任与基本时机，清晰可用的工具/接口提供两类内容的读取、保存与修正及原始对话查询，skill 提供具体维护方法。单靠一段提示词不能保证沉淀，具体指令层级与载体组合仍待设计。

按 [助手形态与实现分界](design-focus.md#已确认的助手形态与实现分界)，上述沉淀/获取时机是 agent 判断与操作的依据，不是必须由机制逐步执行的工作流。系统应提供真实可用的读写和维护入口；若既有工具与说明已足够，走查用于检验协作效果，不据此另造“主动沉淀流程”或“重新认知流程”。尚未验证不能直接推导为需要新增机制。

主动沉淀指 agent 在协作中判断、提炼并保存；被动承接目前指系统保存原始对话及相关事件供查询，不自动把原记录升级为有效事实或决定。若后续增加后台自动提炼，也应遵循相同归属准则，当前未选定该执行机制。

### agent-docs 原则默认生效

项目内容的实质沉淀和维护默认遵循 agent-docs：面向接手者外化必要上下文，区分事实/决定/提案/未知，维护唯一归属，变化时改写对应内容并修复入口，使接续不依赖旧聊天。无需用户逐次点名 skill。

核心意识需要常在；发生相关文档工作时使用完整 skill 的维护方法。普通交流不强制产生文档，普通更新不强制全库治理。助手负责识别并形成应沉淀内容、提供来源，并能调用文档能力完成必要更新；整体盘点、归纳、清理由 docs-workflow 协调，不要求协作助手独自管理整个资产集合。

### 内容触发时机

原则：内容开始需要被后续工作依赖时，沉淀到合适的项目资产归属。

1. **形成有效决定**：需求、范围、约束或方案已明确，后续工作要遵循它，就及时更新对应资产，不必等整个需求讨论完。
2. **需要交接或中断**：准备派工、暂停或换会话，即使还没有结论，也保存当前目标、已确定内容、未决问题与必要来源。

自由发散不要求逐条落文档；沉淀不等于新建文件，优先维护已有归属。具体整理、迭代和清理方式由用户准备的资产机制负责。

## 项目内容何时重新获取

原则：即将依据内容判断、回答或执行，而当前掌握的信息不足或不再可靠时，获取相关资产。

| 条件 | 行为 |
| --- | --- |
| 新会话没有必要背景，或上下文只剩不足以判断的摘要 | 在依赖该背景之前读取 |
| 相关资产已变化，先前认识可能失效 | 下次依赖该内容之前核对和重读 |
| 当前内容足够且仍适用 | 可以复用，不要求每轮重读 |
| 其他 feature 的无关资产变化 | 不因此重载整个项目 |

不能依赖模型可靠地自查“是否忘记”。记录已读资产及其版本是讨论过的工程实现建议，尚未选定具体机制。资产变更通知、版本核对如何实现也尚未确定。

例：已确定“先只支持 GitHub”时保存范围决定；继续谈界面时无需反复读取。派工依赖此范围时核对对应资产；若另一会话改变了范围，应读取并明确处理冲突，不能悄悄沿用旧结论或覆盖当前用户要求。

来源：用户接受“内容需要后续依赖时沉淀；即将依赖但信息不足或可能失效时获取”，并明确资产由其准备的方式处理。

## 会话与业务关系的边界

### 已确认：原始对话是恢复兜底

保留原始对话并提供查询入口，补足资产提炼、摘要或记忆可能遗漏的背景。交出的工作保留原问题与来源对话/消息的线索，便于结果返回时找回必要依据，不要求助手一直记得该工作。

所需能力包括按引用定位、搜索及获取相邻上下文；具体查询接口尚未设计。agent 自主判断何时、获取哪些内容以及读取多深，不固定恢复脚本。原始对话表达当时的交流，不替代当前资产，也不扩大已有授权；来源缺失时不能假称完整恢复。

这是设计要求，不表示本次完整聊天已导出或系统已实现查询。

### 对话与业务对象保持灵活关系

当前已收敛为单项目、一个主要助手对话及并行工作状态可见性，完整形态在 [design-focus.md](design-focus.md) 维护。早期曾比较多对话，现已移出设计范围。feature 为用户通识表达，不是新的插件对象。

单对话可以承接多个议题、需求和工单。问题会在交流中形成、拆分和合并，一段交流也可能只有理解和探索，没有实施产物；不强制业务对象与对话一一对应。

资产和原始记录查询继续用于长期交流、运行中断与上下文重建。助手记忆中的“跨会话”指可跨底层运行或会话恢复延续，不构成重新加入多个用户对话的要求。

## 已提供基础：文档工作流与 RouteLedger

用户明确 docs-workflow 就是之前准备的文档盘点、整理、迭代和清理能力，并提供 RouteLedger 插件。当前按两者已能接入的前提评估充分性和调用时机，不要求先解决接法；本仓库未因此初始化、绑定或改写 RouteLedger 状态。

职责评估：项目内容及必要理由归项目资产，docs-workflow 协调其维护；阶段、Todo、Deferred 和 Constraint 等推进状态可由 RouteLedger 承接；具体执行状态仍由 superagent 负责。助手不再复制这些责任。此分工的精确关联与接口未设计。

调用时机的当前建议（尚非自动化规则）：

- 后续需要依赖的决定或要求形成时，维护相关资产；需要推进或持续约束时使用适用的 RouteLedger 记录。
- 恢复工作或判断下一步时，按需查询资产与相关推进状态，不把所有查询都当作启动全库盘点。
- 阶段结果改变事实或状态时，更新受影响归属；收尾时检查遗留工作与资产准确性。
- 自由发散不强制创建任务或阶段；普通文档更新不强制全库治理。

边界：RouteLedger 的 Deferred 要求未来复审阶段，不能默认承接所有“以后再聊”的想法；有序 Route 与 Current Version 也不等于已覆盖全部并行 feature 调度。两项基础不直接替代原始对话或助理记忆。

## 后续边界

助手先前曾分别倾向“长期助理”和“默认冷启动”，后来区分了项目认知与协作记忆的责任。这些历史倾向不是最终运行机制选择；当前自主与活跃原则见 [design-focus.md](design-focus.md)，剩余选择见 [interaction-proposals.md](interaction-proposals.md)。后续无需重开已确认的信息归属问题。
