# 项目助手第一批渐进式计划（已交付）

本文件保留已接受并分别交付的 A01、A03、A04 计划及范围依据。对应提交为 a04b2e9、0df7745、421d189，均已推送；真实试用仍待进行。当前状态见 [任务板](../task-board.md)，本轮覆盖与纠偏见 [设计审视](design-review.md)；原第二批推荐已撤下，未实施。更新日期：2026-11-05。以下阶段描述保留实施前的计划语境。

## 目标与共同边界

先解决已暴露的首次使用问题，再整理原型仓促的角色、来源和反馈接入，使现有功能可以稳定试用并承接后续修改。

- 保留配置 GitHub 后再使用助手的前提，不新增脱离 GitHub 的助手运行方式。
- 保留单项目单助手、后台调度与 worker 分责，以及已有工单、执行和真实数据来源。
- 结构调整沿用当前模块分层；不新增 Feature 实体、执行调度系统或通用角色插件框架。
- 已有来源消息真实性、工单授权范围、事务关联、操作去重和反馈回程属于必须保持的行为。
- 每个需求单独实施、检查、交付和收束。常规技术细节连续推进；影响目标、职责或用户行为的重要取舍再讨论。
- 使用不影响电脑操作的测试。模拟验证与真实试用分别记录，不用模拟结果宣称模型、桌面或 GitHub 联调完成。

## 需求 A01：安装与可用状态完善

**结果：**用户能够理解配置是否完整、助手是否实际可用，以及缺少什么；不会点击一个指向未创建会话的可用入口。粗估 0.5～1 人日。

| 阶段 | 工作与可审阅产物 | 验收依据 |
| --- | --- | --- |
| 1. 明确初始化事实 | 核查 bundle 默认项、必填配置、setup 与会话创建的实际顺序；区分配置未完成、初始化中、可用和失败。确定必要的状态表达，复用已有事实 | 空配置、缺 GitHub、初始化成功和失败的场景，能从事实说明入口应处于什么状态 |
| 2. 修正安装与入口 | 完善首次启用配置引导和就绪状态返回；面板据实控制助手及工作引用入口，并给出配置或失败原因。首次安装采用什么配置入口由框架现有能力决定，不预先选默认目录 | 模拟首次启用、缺配置和配置完成的检查通过；不会把预先计算的会话 ID 当作已创建会话 |
| 3. 独立交付 | 同步桌面安装步骤和限制，进行必要类型检查与构建，交付本需求 | 用户可单独试用此版本；真实 GitHub 未配置的部分明确标注待验证 |

**本需求不包含：**会话归档或删除后的恢复策略、角色结构整理、Windows shell 适配和新增业务能力。

## 需求 A03：助手与角色接入结构整理

**结果：**角色接入职责明确，后续调整助手不需要在通用会话管理中重复铺开一套生命周期。粗估 1～2 人日，A01 收束后进入。

| 阶段 | 工作与可审阅产物 | 验收依据 |
| --- | --- | --- |
| 1. 分清职责 | 核对工具定义、助手业务、历史读取与接续记录的调用和数据归属；列出必须保持的行为。以现有 app/tools、应用业务与 DSH 会话适配的分层为依据 | 可以明确指出每类规则的维护位置；不引入为假想扩展准备的新层次 |
| 2. 整理助手边界 | 将工具定义移入现有工具层；助手业务保留交接、关联与接续职责；历史读取由会话适配承接。按行为逐块迁移 | 建单、定向答复、状态查询、历史分页与 checkpoint 的接口行为和存储兼容检查通过 |
| 3. 整理角色共用生命周期 | 明确三个固定角色的预设、提示词、工具、模型选择，共用重复的装饰、skill 绑定与释放逻辑；保留当前助手复用研判模型的约定 | 三个角色获得各自应有的工具和指令；加载、释放、重载无重复注册；A01 状态行为保持 |
| 4. 独立交付 | 检查职责与依赖方向，删除迁移过程中不再需要的重复分支，完成相关回归、类型检查和构建 | 本项以保持现有功能行为为验收目标；角色权限或模型行为如需改变，单独提出，不夹带修改 |

**本需求不包含：**重新设计会话恢复策略、引入独立助手模型设置、重写提示词产品行为和新增个人记忆。

## 需求 A04：本地来源与反馈结构整理

**结果：**本地用户消息怎样成为工作依据、工单反馈关联由谁维护、事件返回哪个角色，都有明确归属。粗估 1～2 人日，A03 收束后进入。

| 阶段 | 工作与可审阅产物 | 验收依据 |
| --- | --- | --- |
| 1. 固定当前合同 | 走查助手建单、worker 提问与答复、停止、失败、路由器重新接单和外部来源工作；识别已有来源特判、重复关联写入和反馈目标选择点 | 各路径的用户依据、授权范围、事务提交点和回程目标清楚；重要差异先解决再迁移 |
| 2. 整理本地来源与关联 | 将本地身份与消息转换集中到来源适配边界，明确其与公共准入逻辑的关系；收敛反馈关联的维护归属，覆盖助手直接建单及后台路由重新接单 | 插件消息不能冒充用户；原文与整理内容保持区别；创建失败不留下半份关联；现有记录仍可读取 |
| 3. 整理反馈选择与投递 | 集中工单到反馈目标的选择，明确必要标识和事件语义；继续使用现有 Effects 与 AgentDelivery | 普通进度不唤起助手，派工不冒充模型已开始处理；问题、结果及执行器失败到正确角色；重复事件、中断和重试不破坏回程 |
| 4. 独立交付 | 检查外部渠道责任未被转移，完成定向交接、事务和恢复相关回归、类型检查与构建，更新接口说明 | 本地与外部来源的反馈各归其位；用户不需要靠转述来补交接信息；不维护第二份执行状态 |

**本需求不包含：**新增外部回复操作、图片附件、问题答复接口行为改造，以及调整普通事件是否打断当前讨论的产品策略。这些分别留在 A09、A08、A06 或实际体验后讨论。

## 批次节奏与估计

| 顺序 | 独立需求 | 粗估 | 交付后如何继续 |
| --- | --- | --- | --- |
| 1 | A01 安装与可用状态完善 | 0.5～1 天 | 先获得一个可单独试用的修正版，再决定是否进入 A03 |
| 2 | A03 助手与角色接入结构整理 | 1～2 天 | 收束职责与回归后，再决定是否进入 A04 |
| 3 | A04 本地来源与反馈结构整理 | 1～2 天 | 结束本批，根据试用反馈重新选择后续需求 |

合计粗估 2.5～5 人日，按人工等效工程工作量理解，包含必要验证和文档，不含等待环境或用户反馈，也不是 agent 实际日历工期承诺。各项进入前进一步核查并收紧估计；不简单累加重复检查，也不省略每项的必要验证。

每个需求完成时做一次轻量复核，重点看行为、职责、数据归属与原功能兼容。相关单元和模拟集成检查随实现进行。涉及代码时完成类型检查与构建；既有 Windows 环境测试失败与新增回归分开记录。采用分工时按明确文件与责任拆分，由主 agent 集成；本计划不预先固定 agent 数量。

如果真实试用发现 A05 的 Windows 执行链问题成为阻断，先说明证据和影响，再调整需求次序；不把它静默扩充到 A01 或结构整理中。用户选择暂停、先体验或改变排序时，任务板同步反映安排。

本批已获推进授权，按顺序独立收束；任务板上的其余候选仍保持未排期。用户要求暂停或等待试用时，按相应要求调整。
