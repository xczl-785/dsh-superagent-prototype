# 当前设计重心：理解问题，形成结论、决定或可承接的工作

本文件单独保存当前设计方向，便于继续讨论和修订。它不是最终产品规格或实施计划；[已对齐的信息边界](foundations.md)仍由原文件维护。

本文件维护目标与责任要求。技术机制的待选描述保留 2026-11-03 需求收束时的背景；2026-11-05 已启动首个原型增量，实际选择、已实现内容和验证限制见 [prototype.md](prototype.md)。不能把此处的历史待选状态当作当前实现状态，也不能把首个增量等同于六项能力全部验收。

## 首要目标

> 帮助用户理解项目中的问题与想法，获取必要依据，形成有效结论、决定或可承接的工作。

这是用户已确认的当前设计重心，后续允许调整。整个系统提供交付闭环，协作对话不独自承担全程，也不以持续推进全部已交接工作为目标。不能把本文件中的候选形态直接解释成代码实施授权。

协作连续性强调目标、决定、约束、未决问题和必要反馈能够接续，减少用户整理和转述上下文的负担；不要求所有工作必须放在一个永不结束的模型会话或一个界面窗口中。

“可交付结果”按实际目标判断，可以是经过核实的结论、方案或代码/PR。探索也可以得出不实施或暂缓的结论，不强迫每段交流产生代码。

## 为目标提供的能力

| 能力 | 用途 |
| --- | --- |
| 理解与澄清 | 辨认用户目标，区分现象、猜测、约束和已经确定的要求 |
| 获取工程认知 | 按需读取代码、项目资产及相关证据，有依据地参与讨论 |
| 分析与共同决策 | 比较方向、揭示影响和取舍，帮助用户形成决定 |
| 形成可承接工作 | 明确下一步的目标、产出、边界和依据，避免用户重新整理 |
| 理解相关反馈 | 调查或执行反馈影响当前问题、约束或决定时，能够接续讨论 |
| 延续协作上下文 | 保存必要交流背景，识别沉淀或重新获取的需要，延续适用的协作偏好 |

对话可按需读代码、分析方案，也可委托调查；不默认承担每项工作的全部细节。打薄的是实施与管理责任，不是工程理解和判断能力。工具与运行方式的具体实现仍待讨论，自主组织工作的原则见下节。

### 将 agent 视为行为主体

明确目标与责任边界，提供必要的信息入口、行动能力和引导，由 agent 根据当前任务自主获取依据、组织调查和沟通。常规理解、提问、恢复与解释能力作为前提，不逐句编排对话脚本。

不固定恢复时先说什么、展示多少、按什么顺序读取信息。用户需要更多时，agent 自行继续获取。必要引导保留当前事实与历史讨论、用户决定与助手建议的区别，以及已有系统的职责归属；不因此增加重复状态或项目事实副本。

后续使用走查重点发现信息不可达、能力缺失和职责冲突。普通行为只有在实际使用暴露具体问题时再补充约束。此前场景中的回复、顺序和呈现示例仅用于说明，不是产品必须遵循的流程。

### 已确认：按需活跃，允许相关事件唤起

用户交流、自己发出的调查返回或相关事项需要决定时可活跃；没有需要时可以停下来，不默认持续扫描项目或寻找事情做。活跃后由 agent 按目标自主获取信息、判断是否回应或继续调查。

持续的是协作关系及可恢复背景，不要求持续运行思考。项目资产变化可在需要使用时获取，不要求每次变化都主动发起交流。具体唤起与呈现机制尚未选定。

### 已通过：获取工程认知

- 能主动获取项目资产、代码与相关证据，不要求用户先把工程解释清楚。
- 理解深度由当前问题决定：先了解相关行为、约束和影响范围，再按技术取舍需要深入。
- 区分已核实事实、推测与未知；关键依据不足时补充调查，不以猜测引导决定。
- 对当前讨论需要的工程理解负责。调查可以委托，返回的结论需要自己理解和核对；不因此预设 subagent 架构。

### 已通过：分析与共同决策

- 识别目标、假设和方案之间的矛盾，不仅回答字面问题。
- 有依据地提出建议，说明理由、代价与未确定之处，不把所有判断都交还用户。
- 根据用户反馈修正认识，逐步形成有效结论、决定或可承接工作。
- 推荐不等于已接受决定；补足常规细节不等于新增产品目标或扩大范围。

### 能力要求与实现载体分开

六项能力及讨论中的责任边界均已获用户逐项同意。确认的是“需要做到什么、负责到哪里”，不代表已验证实际使用闭环。

提示词、skill、工具、MCP、插件、钩子及其他机制都可作为实现载体，不预设一项能力对应一个载体。用户已指定 docs-workflow 与 RouteLedger 可作为现成基础评估，按“能够接入使用”的前提讨论；具体接法、其他载体选择及委托机制未定，不能将能力讨论视为实现完成。

### 已通过：形成可承接工作

能提取有效要求、确定合适的下一步范围、表达产出与完成依据，并保留必要背景和来源，使接手者无需用户重新整理即可正确开展工作。区分用户决定、助手建议、探索假设和未决问题，不把这些混入同一要求。

产物可以是调查、验证或实施工作，不要求一次拆完大需求；不默认替执行者写完整技术计划，也不承担调度与全部执行跟踪。进入现有执行体系的工作通过工具交接为工单；纯讨论结论不强制建单，具体接口和交接格式尚未设计。

### 已通过：理解相关反馈

理解结果回答了什么、依据和未知，识别其对假设、约束和决定的影响，将报告转为有效沟通。当前问题解决即可收束；关键未知可补充调查；重要取舍回到用户。

对理解与判断负责，核对深度与重要性、证据缺口相称，不重复执行全部调查或验证，不未经判断就接受报告结论。调查与实施反馈的不同责任见下节。

### 已通过：延续协作上下文（后续重点）

能接续当前目标、已定内容、未决问题和暂缓方向；保持用户决定、助手建议及假设的不同身份；信息不足或变化时按需重新获取；延续适用偏好并尊重当前要求；区分并行 feature 与讨论背景。

负责正确使用和接续必要背景，不要求始终记住全部历史。用户明确指出这是后续设计重点，涉及会话接续、上下文压缩、资产获取、助理记忆和并行隔离，需要通过具体场景检查，不能将“已有摘要或长期记忆”等同于解决。

### 已通过：理解与澄清用户意图

区分现象、猜测、想法、决定与行动要求，识别用户期望的结果及其与所提手段的差异；维护目标、范围和明确约束，正确理解讨论中的变化。

上下文可推断或调查可获得的信息先自行理解；需要用户表达偏好或关键取舍时聚焦澄清。允许想法暂时模糊，不强求完整需求或急于派工。不能将意图推测视为承诺；理解偏差时修正相关结论。

## 两类结果与接续责任

| 结果 | 责任 |
| --- | --- |
| 为当前讨论发起的调查、实验或方案比较，包括 subagent 返回的结果 | 分析依据、回答当前问题，完善认识或帮助用户作出决定，属于讨论闭环 |
| 从本对话交接出去的实施工作，包括 PR、验证、阻塞和评审发现 | 当反馈影响当前问题、约束和决定，或用户要求讨论时接续；不默认跟踪全部执行事件 |

讨论闭环为：`提出问题 → 获取依据 → 分析讨论 → 形成结论或下一步`。

执行反馈回到讨论时，只接手其中需要理解、澄清和决定的部分。PR 来源于本对话，不意味着本对话要承担其全部后续；PR 跟踪、评审处理和执行管理仍属执行体系。

“继续”的方向只依据当前已经明确的用户目标。比较方案就回答可行性；实施发现原方案不可行就重新讨论该取舍；目标满足就可以结束。不能因结果返回自动展开下一阶段，也不能把单个阶段完成解释成整个方向完成。

## 不默认承担的责任

- 编码、测试、技术自审和 PR 操作的具体实施全过程。
- 并发、重试、恢复、工单状态维护等执行调度。
- 整个项目资产集合的治理；助手默认遵循 agent-docs，主动形成应沉淀内容并能调用文档能力完成必要更新，整体盘点、归纳、清理和迁移由 docs-workflow 协调。详细归属和时机见 foundations.md。
- 所有 feature 的排期、依赖协调、集成管理及全部执行细节。
- 代替用户决定目标和重要取舍，或把助手推断视为用户决定。

## 庞大需求如何推进

不以“全部需求梳理完”为开始下一步工作的前提。每轮判断：目标和已知约束是否清楚，这一步要产出什么及怎样判断有用或完成，剩余不确定性是否能由接手者调查和决定。

如果仍有会改变工作方向、必须由用户取舍的关键问题，继续讨论；否则可以在授权范围内交接调查或实施。不要求先设计完整系统，也不把庞大方向直接塞进一个实施工单。

典型过程：`模糊方向 → 明确下一步 → 调查或实施`；讨论所需的调查结果回到讨论，实施反馈按上述接续责任处理，不要求协作对话全程监督。

例如“改造成个人项目助手”的第一步可以是调查现有会话扩展方式、比较接入路径及限制，结果回来后再确定首个实施范围。

整体完成应对照已经明确的范围与预期结果；几个 PR 完成只能证明相应阶段的工作，不能自动证明整个方向已实现。

## 沿用现有 superagent 的责任

### 对话与影响操作分开

对话承载正常交互。创建工作、向工单追加要求、停止、重试和其他状态变更，通过用途明确的工具/接口执行；文字讨论或宣布准备操作不等于已执行。操作结果以接口返回及实际状态为准。

agent 需要理解工具用途与影响、作用对象、前提和限制、返回结果，在当前授权内自主选择。后台调度和 Engine 承接既有准入校验与工单操作，不让整段助手对话成为多个工单订阅的普通 Thread。

工单由本对话产生，不代表订阅此后全部交流。选定内容的定向交接需保留原始意图、来源和适用范围；具体适配接口尚未设计。执行报告是事实或待决问题，不自动成为新的执行要求。

### 已确认方向：工单交接与反馈回程（高重要性，后续设计重点）

用户明确要求将此处标为高重要性：它关系到助手是否如实表达进展、原始意图与授权是否保留，以及必要反馈能否回到协作中。以下是已接受的方向，不代表具体订阅、投递或接口方案已定或已实现。

- 工单创建成功并取得标识，即可告诉用户“已创建，等待执行”，不必等待 worker 启动；创建失败不能宣称已交接。
- 执行端确认派工后，再根据实际确认的语义告知启动。创建、排队、派工成功与模型实际开始处理应可区分，不将接口接受任务表述成已经开展实施；PR 通常是后续产物。
- 创建工作时配套建立与本项目助手的反馈关联，避免依赖 agent 随后记得再订阅。相关启动、待决问题、阻塞及结果有明确回程；普通进度可查询或进入面板，不要求每次变化都唤醒助手或通知用户。
- 工单事件订阅是“执行状态或报告回到助手”；现有 Thread 订阅是“后续消息进入工单”。两者方向与责任不同，不将整个助手对话订阅给 worker。
- 保留实际用户请求的来源和原始消息引用、助手整理的工作内容及资产依据、工单与助手的反馈关联。助手是工具调用者，用户请求是意图与授权的来源；不能将助手整理的文本伪装成人类消息，不能将整段对话交给后台重新理解以替代定向交接。
- 复用既有准入、执行、事件和消息投递能力，助手理解返回的结果并按当前目标接续；不因此增加一套执行调度系统或要求助手监督所有事件。

后续设计需重点核对：本地用户来源与授权如何进入既有准入链路；创建与反馈关联如何协调以免遗漏早到事件；启动事件的准确含义；事件的投递对象、唤起与查询边界，以及中断恢复、重复事件和工单结束后的关联处理。它们是待解决的设计问题，不在此预设新状态机或具体实现。

最小使用闭环为：`用户与助手讨论 → 工具创建工单并关联反馈 → 返回创建结果 → 既有执行链路派工 → 相关事件返回助手 → 按当前目标接续沟通`。现有支撑与缺口见 [current-system.md](current-system.md) 的“创建、启动与回报的现有边界”。

### 使用语义与插件对象分开

feature 是用户表达功能、需求或模糊想法时的通识语义，不是插件设计对象。当前不建立 Feature 实体、状态机、生命周期或其与 Ticket/阶段的映射模型，也不把它排为后续待设计层。

用户需求的形成、拆分与变化自然体现在交流、资产及工具使用中。明确操作落到已有对象：Ticket 表达授权执行工作，Assignment 表达一次执行承担，PR 表达代码交付，适用的 RouteLedger 记录表达推进安排。既有对象足以支撑主要场景，接口适配仍需核验。

| 责任 | 现有承担者 | 协作对话边界 |
| --- | --- | --- |
| 消息准入、关联、工单创建和恢复 | router 与 Engine | 交接明确意图、查询事实，不维护另一套工单状态 |
| 工作目录、会话、并发、输入投递与恢复 | executor 与 Sessions | 不调度底层执行细节 |
| 技术调查、实施、检查、自审与 PR | worker | 可以委托调查和实施，不重复完整执行过程 |
| PR 反馈、报告及人工问题转达 | worker 与现有回传机制 | 必要时接续相关讨论，不负责全部 PR 后续或吸收全部日志 |

现状证据见 [current-system.md](current-system.md)。新协作对话如何接入现有能力尚未设计，不能视为已经接通。

多个工单并行不等于已有大型需求的跨工单依赖规划和集成管理。若实际需要此能力，应单独明确归属；不能让协作对话靠记住所有事情隐式承担它。资产整理继续交给用户准备的机制。

## 已确定的产品形态

### 前台协作与后台调度分责

保留原主 Session 的后台调度职责，提供面向用户的独立协作助手角色。前者处理来源事件、准入、路由和结果转达；后者围绕用户当前问题调查、思考和讨论。日常主要协作入口只有一个，不把后台调度包装成第二个项目助手，也不取消 worker 的直接操作入口。

当前助手的身份是“服务本项目 DSH 界面用户的项目协作者”。GitHub/飞书等来源继续由原主 Session 按现有准入、路由、执行与渠道回复链路处理；助手不自动承接这些来源的需求对话，也不因读取某个 Thread 就成为其回复者或持续处理者。

用户可让助手分析 Issue/PR，或带着外部待决事项到这里讨论；需要将结论提交回工单或渠道时，通过定向工具完成并保留对象、来源和授权依据。原主 Session 继续承担原来源渠道的既有交接，助手负责与当前用户的交流，避免重复回应或扩大服务范围。未来是否承接外部需求探索属于范围扩展，不在当前默认身份内。

这里确定的是责任与展示边界，尚不决定是否必须采用两个独立运行实例或具体接入方式。

高级设置提供复选项“显示后台调度会话”，默认不勾选；说明用途为查看 superagent 事件路由与调度过程。隐藏仅影响展示，不停止后台运行，不改变事件、工具与记录。显示时使用“后台调度会话”与“项目助手”区分角色。能否同时控制 DSH 会话列表及插件面板入口，仍需核对框架能力，当前未实现。

范围限定为单个 DSH superagent 项目：一个主要助手对话，配合已有工作对象的并行状态视图。多助手对话移出当前设计范围，不再作为需要同时支持或继续比较的方案。用户跨多个项目时，各项目分别服务，不新增跨项目总助理。

助手对话承接当前关注的问题、想法和决定；同一对话可先后讨论多项工作，不强制一议题或一工单对应一对话。后台多 feature 执行并行与用户注意力集中处理当前问题可以同时成立。

并行执行与跟踪复用现有基础，人工仍负责合并。助手不因此接管全部 PR 后续或持续监控全项目。底层执行器与调查会话不受“单个用户助手对话”限制，具体会话恢复、压缩和重建方式仍未选定。

### 并行工作状态视图

用户与助手都可查看项目全局状态。面板承载并行工作的可见性，对话承载当前注意力；需要全局背景时按需查询，不把全部状态长期塞入对话。

面板应提供工作目标、当前阶段与执行状态、阻塞与待决定事项、关联工单/PR/结果、待评审和待人工合并情况。具体布局及展示粒度尚未设计。

面板是已有状态的统一视图，复用 superagent 的执行事实与适用的 RouteLedger 推进记录，不维护平行状态。助手需要能够查询同一份底层信息，不要求通过截图读取；具体数据来源关联与查询接口尚未设计。

回拉现有工程后已确认 Overview/Execution 与工单详情具有部分对应能力。因此这里确定的是并行状态可见性的需求，不等于必须新建面板；后续讨论现有面板怎样满足该需求，不新增 feature 设计层。

已通过的复用方向：保留原管理面板，补充项目助手入口、具体工作引用及同源查询能力，不另建平行面板。用户可由面板携带工作引用进入讨论，也可由助手提供操作后工作记录的入口；具体布局与交互尚未实现。

### 单对话下的反馈接续

相关反馈回到本项目助手，保留工作及原请求的来源线索，便于定位它回答的是哪件事。无需设计多个助手对话之间的投递、订阅和承接转移。普通反馈不默认改变当前讨论焦点；是否需要继续获取和解释，由 agent 依当前任务判断。

## 工程机制如何服从目标

| 方面 | 应提供的支撑 | 需要避免的问题 |
| --- | --- | --- |
| 代码职责与任务交接 | 原始意图、有效决定、执行范围和相关反馈有可追踪关系；用户不用充当人工转述者 | 只派一句工单标题、丢掉约束；必要反馈无法接续；业务对象强制一一绑定 |
| 上下文压缩或重建 | 恢复当前目标、约束、决定、未决问题及必要来源；缺少细节时可以按需获取 | 压缩后重复询问已明确事项、重新打开已解决问题，或将旧方案当作当前决定 |
| 项目资产与助理记忆分工 | 工程认知依据当前资产，协作背景通过适用记忆延续；内容分界见 foundations.md，记忆维护见 assistant-memory.md | 为追求“记得更多”而复制工程事实，或为追求冷启动而丢失必要交流背景 |
| 界面与对话组织 | 用户可以顺畅延续交流，也能独立开展并行工作 | 迫使用户适应后台会话切换、自己搬运和拼接上下文 |

这些机制各自有责任，但其形式和复杂度都应由协作目标决定。冷启动、持续会话、压缩、检索或向量化不是需要先证明成立的产品目标。

连续协作也不意味着保留一切历史或沿用过时认识。项目发生变化时，应按 foundations.md 的获取原则核对；新旧信息冲突不能靠悄悄覆盖解决。

## 后续如何判断方案是否合适

先沿着一个实际场景检查：用户提出问题或想法，经过必要的交流和调查，得到有效结论、决定或可承接的工作；若有相关反馈，能在需要时恢复讨论。

- 用户是否被迫反复整理和转述本已表达清楚的背景？
- 有效决定与约束在上下文重建、派工和结果回传后是否仍然成立？
- 助手是否能面对当前工程变化更新认识，同时延续必要的交流背景？
- 用户是否能理解当前进展和待决定事项，而不必理解内部 agent 和会话结构？
- 现有执行能力是否得到复用，协作对话是否被迫承担重复调度或全部实施细节？

能力覆盖初查与跨数日使用走查已开展，尚非运行验证。已据讨论确认原始对话查询作为恢复兜底（见 foundations.md），并明确 docs-workflow/RouteLedger 可作为现成基础评估。

当前目标、能力及使用原则已完成需求层收束；助手记忆能力闭环见 [assistant-memory.md](assistant-memory.md)，整体已有基础、需补齐能力与后续状态由[入口](README.md)汇总。若后续需要走查，继续聚焦信息入口、必要触发和责任缺口，不逐句编排行为。具体接入与技术选型仍未获进入决定；模拟中的假设不能提升为已确认需求。

上述助手身份与服务范围已明确，用户交流、形成工作、工具交接和必要反馈接续的最小流程概念走查已收尾，场景及实现缺口见 [interaction-proposals.md](interaction-proposals.md)。用户要求本轮讨论至此结束；运行结构与其他实现待未来另行启动设计。前序对 DSH 会话、压缩、持久化和消息投递的分析仅作已有能力线索，不作为已采纳的助手运行方案。

## 讨论来源

本次 Codex 对话中，用户逐步确认目标、六项能力、自主原则与已有基础，随后确定单项目单助手、后台调度分责及显示设置、交流与影响操作分开。用户明确 feature 只是使用语义，不进入插件建模。并行状态需求应以已有对象与界面核对；底层运行、布局及具体接入仍未定案。
