# 助手设计与实现审视：覆盖、偏移及纠偏

2026-11-05，针对用户提出“先不安排下一批，回看已有设计、功能和闭环”的审视，并按随后确认的 agent 自主原则补充纠偏。检查代码基线为 `b1d27de`；此后的变更仅为文档，未改产品代码、提示词或客户端配置，未新增开发批次。

## 结论与依据

当前交付实现了协作助手的工单交接、反馈回程及有限上下文恢复基础，尚未证明原设计的完整协作能力。主要偏移发生在后续规划和覆盖说明：持续围绕会话、工单补功能，未按原始目标评估资产沉淀/获取和助手记忆闭环。原型缩减与后续规划偏移应分开判断。

进一步确认：只纠正排序仍不够，原任务板把需求场景和 agent 自主行为直接当作实现项，才是需要纠正的推导方式。形态与分界现由 [design-focus.md](design-focus.md#已确认的助手形态与实现分界) 维护；任务板已逐项改成支撑能力、核查对象或可选方法。下文“协作闭环未验证”描述行为证据不足，不自动表示必须新增代码或由机制编排全过程。

审视依据为 [design-focus.md](design-focus.md)、[foundations.md](foundations.md)、[assistant-memory.md](assistant-memory.md) 中已确认的要求。首个增量与第一批缩减范围由 [prototype.md](prototype.md)、[first-batch-plan.md](first-batch-plan.md) 解释。历史待选机制由 [interaction-proposals.md](interaction-proposals.md) 保存，不能自动视为已经确定的规格。源码、提示词及模拟测试支持实际实现判断，不替代用户需求或真实使用证据。

本轮检查助手业务与工具、来源适配、反馈关联、运行时组装、会话历史/装饰、资源查询、接续 KV、角色提示词及助手测试，沿现有执行/投递接口追踪相关路径；不是对上游全部代码的全面可靠性审计。主审与独立只读复核交叉核对了主要判断。

## 原始目标与实际覆盖

| 已确认能力 | 当前支撑 | 本轮判断 |
| --- | --- | --- |
| 理解与澄清 | 提示词要求区分讨论、决定和行动；模型可读取真实文件与工作事实 | 有行为引导和信息入口；模型在模糊意图下的实际表现未验证 |
| 获取工程认知 | 文件读取/搜索入口、同源工作查询、外部原始对象读取 | 基础入口存在；调查委托及宿主扩展能力的实际可达性未验证 |
| 分析与共同决策 | 提示词允许分析比较和不实施结论，不强制讨论建单 | 设计与指令未改成纯问答；缺乏真实讨论和多轮决策的行为证据 |
| 形成可承接工作 | 引用真实用户消息，保留原文与整理内容，事务内建单和反馈关联，定向追加/停止/重试 | 主要工具合同有实现和模拟检查；不是完整协作能力已验收的证明 |
| 理解相关反馈 | 需要沟通的报告、问题和结果返回助手，普通进度不唤醒，查询当前状态 | 回程机制有覆盖；理解反馈、核对依据和接回当前目标仍依赖模型，未完成真实验证 |
| 延续协作上下文 | 原始历史分页搜索、消息引用、单份 checkpoint、当前工单查询；提示词要求核对资产 | 部分实现；资产维护/获取、基本记忆、按引用定位邻近历史等尚未形成完整闭环 |

“有工具”“有提示词要求”“模拟合同通过”“真实协作有效”是不同证据层次。后续状态说明应分别表达。

## 发现及纠偏结论

### F01：后续排期偏离目标覆盖，不是原型全部做错

**性质：规划偏移，已纠正文档状态。**原型暂缓个人记忆有接受依据，第一批 A03 也明确不含新增记忆；这不等于永久后置资产与记忆。原第二批推荐 A02→A06→A07，并给 A11 增加“基本协作闭环试用后再进入”的门槛，未说明这些依赖如何来自已确认目标。

场景：纯探索形成了后续会依赖的范围决定和持续协作背景，即使没有工单，也需要适当沉淀和后续获取。等待工单答复、归档等功能完善，不能成为上述能力的固有前提。

依据：[design-focus.md](design-focus.md) 的首要目标、两类结果与接续责任；[foundations.md](foundations.md) 的沉淀和重新获取时机；原 [第二批建议](next-batch-plan.md)。本轮撤下其当前推荐地位，保留候选及讨论依据，不直接把 A11 前移当作已完成纠偏，也不替换成新批次。

用户随后确认的纠偏已落实到任务板：A02 只保留宿主运行边界核查，A06 不再是“准确答复”独立流程，A07 区分历史访问与认知接续，A10 区分能力接入与资产维护行为，A13 保持可选方法。每项先查现有工具与说明是否足够，不能只把原场景换成新标题继续排开发。

### F02：资产维护被表述为“有读写和 skill”，完整闭环尚未证明

**性质：覆盖与验证缺口，不能判为完全没有文档能力。**[assistant 提示词](../../prompts/assistant.md) 明确要求维护原资产、遵循 agent-docs 并在依赖历史前核对当前文件；[Sessions](../../src/app/sessions.ts) 提供文件、skill 等基础入口。因此“已经变成没有文档意识的工单机器人”也不符合证据。

但原要求是：识别需要后续依赖的内容→维护正确资产归属→内容变化时更新原归属和入口→再次依赖时取得当前依据。当前 [助手测试](../../tests/assistant.spec.ts) 未证明这条路径；[模拟宿主](../../tests/fixtures/host.ts) 的技能注册、系统提示词和工具限制使用桩，不能证明真实环境中 docs-workflow/agent-docs 可发现、可读取及可执行。

场景：用户确定“保留旧格式”→只保存 checkpoint 而未维护对应资产→另一轮修改了资产→恢复后仍用旧背景作判断。现有持久化测试证明文本能读回，不能证明这个场景被正确处理。

纠偏：把主动沉淀、按需重新获取及正确维护归属列为 agent 行为走查，而非默认开发流程；系统只对具体的访问、操作或说明缺口补足支撑。文档维护和适用的 RouteLedger 推进记录责任不同，不能因 A10 把它们放在同一候选项，就认为二者必须一起就绪才能开始维护项目资产。

### F03：基本助手记忆未实现，不能用 checkpoint 或历史搜索代替

**性质：已确认要求尚未实现，且规划摘要过度简化。**[记忆篇](assistant-memory.md) 包含持续协作背景及偏好，主动识别和沉淀、明确表达与推断的区别、范围/来源/有效性、查询新增修正停用删除、按需获取后的适用性判断、当前要求优先、避免重复、忘记后不由旧对话自动再生。

现有 [KV](../../src/kv.ts) 仅有接续文本、消息依据、操作记录和工单关联等；[Assistant](../../src/app/assistant.ts) 的 checkpoint 只是替换一份文本。没有上述记忆操作及使用闭环。首个增量暂缓此能力是已接受的缩减；把它描述成只缺一个偏好 CRUD，或把历史能查到当作记忆可用，则不准确。

场景：用户表达稳定沟通习惯→后续按当前问题获取并判断适用性→用户纠正或要求忘记→之后不再默认使用，也不从旧聊天自行写回。当前原型不能据记忆工具合同完成此场景。

纠偏：恢复完整需求引用；将待实现的查询/读写/维护支撑和操作语义，与 agent 的沉淀、检索时机及适用性判断分开。不借本轮选定数据库、向量检索、默认加载策略或后台提炼；回顾提炼 skill 仍是可选方法。

### F04：恢复能力部分成立，说明不能覆盖全部接续要求

**性质：已声明的实现缺口及证据范围不足。**[Sessions.history](../../src/app/sessions.ts) 按事件位置读取/搜索，并返回用户消息引用；尚无根据消息引用直接定位并读取邻近讨论的工具。[Assistant.recovery](../../src/app/assistant.ts) 加载单份接续文本，不能单独证明并行议题或资产变化后能正确恢复。

场景：只知道旧消息引用，原因在前后讨论；或隔天恢复时项目资产已被移动/修订。分页搜索提供基础兜底，仍需按需找回依据并核对当前资产。原型保留相关局限，不能把“持久化重开测试通过”泛化为所有恢复情况通过。交接只提取消息文本，未自动交接图片/附件引用，这一限制也已声明。

纠偏：区分原始历史、讨论接续、资产和记忆四种责任；继续让 agent 自主选择获取深度，不把场景例子编成固定恢复脚本。

### F05：部分底层能力的可达性未知，不能仅凭名称下结论

**性质：待核实，不是已确定的缺陷。**[Sessions](../../src/app/sessions.ts) 中助手继承工具白名单不含所有宿主扩展工具。核查本地 Harness `dsh-tools` 的 `restrict` 合同后，确认它过滤继承工具，而当前 scope 自身注册的工具不受同样过滤。因而不能仅因名单没写 subagent 就判定助手不能委托调查；也不能因有 skill 工具就判定文档工作流或 RouteLedger 已接通。

场景：助手要委托调查，或调用文档/推进能力；工具是否可用取决于宿主实际安装、注册作用域及角色预设。原设计允许委托调查，但没有要求固定 subagent 架构。

纠偏：能力可达与操作成功需有针对性证据；在本轮报告中保持未知，不以未知为由宣称必须重写会话层或新建一套调查系统。

### F06：会话恢复的新策略属于提议，尚未越界实施

**性质：文档外新增的待选产品规则。**原第二批 A02 提出的“主动打开时恢复归档”“删除后显式重建”“目录不匹配阻断交接”是在原恢复目标上增加的具体策略。文件已标注建议、待对齐，代码尚未实施，因此不属于已偷偷添加的产品行为。

纠偏：保留问题和建议背景，撤去实施推荐地位；这类生命周期、删除和目录归属策略后续需要根据宿主合同和用户选择决定，不能从原文直接推导为唯一方案。

### F07：验证集中于操作合同，不能据通过数量判定设计目标完成

**性质：验收覆盖不平衡，原记录已保留真实验证限制。**[助手测试](../../tests/assistant.spec.ts) 覆盖来源真实性、建单去重、定向输入、反馈、事务及数据库重开等，确有价值。历史全量 1193 通过/43 个基线失败只反映当次自动化结果；本轮不重跑、不把它当新验收，也不作为资产维护、记忆使用或真实模型协作效果的证据。

纠偏：判断协作目标时，分别看下表各条闭环的入口、行为、落点和可观察结果。工具合同自动化检查、能力可达性核实和 agent 行为验证各有用途，不能互相替代；行为未验证也不能直接变成代码开发任务。

## 闭环走查

以下为源码与文档推演，未执行真实模型、桌面或外部渠道联调。

| 场景闭环 | 可确认的机制 | 未闭合或未验证处 |
| --- | --- | --- |
| 问题→查工程依据→比较→结论/暂缓 | 文件和工作事实入口、讨论不强制建单的提示词 | 真实获取、判断和有用结论未验证；调查扩展可达性未知 |
| 有效决定→维护原项目资产→后来依赖时读取当前资产 | 文件读写基础与资产维护引导 | 文档能力接入和主动维护/重新获取未形成验证证据 |
| 持续协作信息→记忆→按需获取/判断适用→使用→纠正/停用/忘记 | 原始需求完整存在 | 基本记忆系统及使用闭环未实现 |
| 用户授权→定向建单与关联→派工→问题/结果→当前讨论 | 原始来源、事务关联、真实状态、持久化回程；有模拟检查 | 实际模型理解及真实客户端效果未验证；附件自动交接缺失 |
| 中断→接续背景→找回原始依据→核对当前资产和工单 | 历史分页搜索、checkpoint、工单查询 | 消息引用定位/邻近读取、变化后认知修正和部分会话生命周期未闭合 |

## 保留的设计与本轮纠偏边界

以下实现有原文依据或属于合理技术选择，本轮未发现因此需要推翻的证据：

- 单项目单主要助手，后台 router 与 worker 分责，复用现有面板和同源查询；不自动接管外部渠道。
- 对话与操作分开，原始用户请求与助手整理内容分开；建单、排队、派工、模型活动据实区分；工单创建事务内建立反馈关联。
- 只交接选定内容，不把全部聊天订阅给 worker；普通进度不唤醒助手，不因反馈自动启动下一阶段。
- 沿用 Engine、SQLite、Effects 和 AgentDelivery，三个固定角色共用生命周期；没有发现另建 Feature 实体或平行执行状态机的证据。
- 原型复用研判模型、采用单份接续文本，以及保留 GitHub setup 前提均已有范围记录；具体技术名词未出现在原始需求中，不等于新增了产品需求。模型和上下文策略的适用效果仍待验证。

本轮完成的是：明确助手形态目标及 agent/系统分界，逐项改写任务板，纠正覆盖表述、记录缺口与待选策略，并撤下原第二批推荐和无来源的记忆进入门槛。已确认目标保持，产品代码未修改，不新增记忆方案或架构重构，不形成下一批排期。后续只依据具体支撑缺口讨论实现，不能沿旧推荐或直接从场景自动开工。
