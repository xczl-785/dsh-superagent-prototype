# 交互与执行闭环：待评估提案

本文件保留助手在讨论中提出的候选设计，供继续比较。[信息边界与沉淀/获取时机](foundations.md)已对齐；后续讨论形成的[当前设计重心](design-focus.md)单独维护。评估以下提案时以该重心为依据，本文件不能作为已批准的产品规格或实施计划。

## 角色、对话和工程认知分别讨论

单项目、单个主要助手对话与并行状态可见性的需求已确定，正式归属见 [design-focus.md](design-focus.md)。协作助手与后台调度分责、调度会话默认隐藏且可通过设置显示已确认；以下只保留当前范围内尚未选定的工程建议。保留现有管理面板并补充助手入口、工作引用和同源查询的方向已通过，具体布局和接口仍待设计。

用户助手对话数量已收敛，不等于底层只能有一个执行或调查 agent。用户提出过冷启动 agent 和权限受限 worker 的可能性，尚未比较到实施层面。

仍需区分以下问题：

1. 用户面对的身份与协作体验是否持续。
2. 单助手对话与状态面板的布局及交互。
3. 底层模型是复用历史、压缩、重建上下文还是冷启动。

底层恢复、压缩或重建仍可比较。早期多助手对话及其反馈投递讨论已被单对话决策替代，当前不保留为待实现扩展。

## 几条 PR 诞生路径

| 场景 | 候选闭环 |
| --- | --- |
| 模糊想法 | 沟通 → 形成可承接的调查或实施工作 → 在相应授权内交接；调查结论回到当前问题，实施反馈仅在需要讨论时接续，不要求一次梳理完整需求 |
| 明确小修改 | 确定作用范围 → 在现有授权内派工 → PR → 原交流处交付，不强制完整需求流程 |
| 执行或评审发现新问题 | 带回具体问题 → 讨论决定 → 继续原工单或派独立任务 → 更新原 PR 或新建 PR |
| 纯探索 | 沟通/调查 → 结论、暂缓或未决问题，可以完全不产生 PR |

候选交接内容：原始请求、明确决定、有效约束、尚未确定的问题、相关资产及其适用版本。不能仅压成工单标题，也不能把助手建议当成用户决定。

代码完成、PR 可评审、PR 合并、目标验收及资产更新是不同状态。这些状态由相应责任方维护，不因此要求协作对话全程监督。资产如何更新由用户准备的机制负责，本提案不规定具体文件流程。

## 对话接续与任务回传

原始对话保留、可查询以及工作保留来源线索已获确认，正式边界在 [foundations.md](foundations.md) 维护。建单成功即可回复、派工后据实说明启动，以及创建配套反馈关联、保留用户来源与授权依据的方向也已通过，正式要求见 [design-focus.md](design-focus.md) 的“工单交接与反馈回程”；用户将其标为高重要性设计重点。以下仅保留具体机制的候选考虑。

曾建议记录对话/来源消息、执行依据、工单、PR、回传位置之间的关系，以便：

- 一个项目助手对话可产生和讨论多个任务。
- 再次询问旧任务时查询原任务，不自动重复派工。
- 与当前问题、约束或决定相关的结果、阻塞和问题可以回到交流处；不要求全部 PR 事件回传或自动展开下一阶段，日志留在执行详情。
- 对话里只是讨论，不应因关联多个任务就将每句话广播给所有 worker。

交流与影响操作分开已确认：实际状态变更通过工具/接口，助手需要理解用途、对象、前提、限制与结果，不把长期对话直接套用外部 Thread 的订阅扇出。定向交接、来源关联和纠错的具体接口未设计；现有可复用能力与限制见 [current-system.md](current-system.md)。结果到达不默认切换当前关注点，具体获取与解释由 agent 按需判断。

## 存储与记忆的候选实现

已确认的是项目资产与助理记忆的责任不同；以下实现选择尚未确认：

- 项目资产、原始对话与助理记忆的内容责任已确认，见 foundations.md；物理存储与执行记录的关联方式仍待设计。
- 逻辑分离可以先用不同表表达，不必采用多个数据库。
- 向量索引可以只是助理记忆的可重建检索索引；按条目变化更新，不必因项目文档整理反复重建助理记忆向量。
- 助理记忆的来源、适用范围、明确表达/推断和有效性需要可辨认，已在 [assistant-memory.md](assistant-memory.md) 确认；具体字段、数据结构与状态表达仍未选择。
- 已落入项目资产的工程结论，可以只留下引用，不在记忆里维护副本。

用户关心向量化频率，并提出记忆与数据库可能需要分开；这尚未形成技术决定。基本记忆维护要求、获取使用闭环及回顾提炼扩展在 [assistant-memory.md](assistant-memory.md) 维护；自动提炼、纠正、删除和跨项目共享的具体实现仍未设计。

## 已走查场景与后续范围

六项能力已通过，并已进行跨数日、并行工作和中断恢复的概念走查。以下场景可用于后续检验信息入口和职责缺口，不再细化常规行为脚本；具体接入暂不考虑：

1. 连续多轮自由探索，同一窗口里方向逐渐变化。
2. 数日后恢复项目助手，需要部分旧沟通背景，但相关 feature 资产已经变化。
3. 原工单已结束，用户回到助手讨论后续调整。
4. 多 feature 并行，用户从面板了解全局，在助手里查询或讨论某项工作。

走查已支持以下方向：结果到达不强制切换当前关注点；恢复需区分当时讨论位置与当前工程事实；阶段交接或 PR 完成不等于整个方向完成。原始对话可查询作为兜底，常规查找、核对和解释由 agent 自主组织。这些方向不规定固定对话脚本，也不是运行验证。

### 最小协作流程收尾走查（2026-11-03）

用户要求完成流程走查后结束本轮讨论，不进入实现设计。以下以“工单 A 修改导出功能，助手同时与用户讨论 B 的界面想法”为共同背景，检查已确认原则能否承接后半段流程。步骤是推演证据，不是固定 agent 脚本；表中处置属于对已有边界的应用，不代表用户逐项批准了新机制。

| 场景与逐步推演 | 设计覆盖及风险 | 留给实现设计的核验 |
| --- | --- | --- |
| A 建单成功但暂无执行名额 → 助手告知已创建、等待执行 → 派工确认后据实说明启动；若启动失败，查询工单实际状态并说明 | 已明确：建单与启动分开；无须让用户等到 worker 运行才得到回应 | 创建接口结果、启动事件语义、失败状态的可达性；当前尚未接通助手 |
| A 的 worker 询问“是否保留旧格式” → 回报携带 A 的标识和问题 → 助手按需找回 A 的约束并与用户讨论 → 将用户决定通过定向工具送回 A | 已明确：反馈返回助手，决定通过工具追加，不把 B 的聊天广播给 A；助手不替用户作重要取舍 | 人工问题与答复的准确关联、问题是否仍有效、定向答复接口 |
| A 执行中，用户要求缩小范围或停止 → 助手针对 A 调用追加或停止工具 → 依据结果说明变更是否生效 → 若旧结果随后返回，先核对当前工单和有效决定 | 原则可覆盖；风险是把口头改要求当成已送达，或将变更前结果误认作满足新目标。停止不等于撤销已经发生的外部操作 | 变更生效依据、追加与停止的状态限制、变化与回报交错时如何识别；具体规则未选定 |
| 助手正讨论 B，A 返回普通进度、待决问题或 PR → 识别其属于 A → 必要时查询来源与结果 → 按当前目标判断是否提示或接续，B 的讨论不因任意事件自动丢失 | 已明确：单助手可以承接并行工作，反馈不强制切换焦点；PR 返回不自动扩大后续工作 | 事件可查询性、必要事件唤起、工作引用及未处理问题的可见性；不预设优先级状态机 |
| 用户隔天回来，底层上下文已压缩，A 的资产也被整理过 → 查询当前工单和相关资产 → 缺少理由时按来源定位旧对话 → 区分历史决定与当前事实，再回答或继续工作 | 已明确：资产作为工程依据，原始对话补遗漏，助手记忆承接适用协作信息；不要求一直记住 A，也不因失忆重新建单 | 来源引用在资产整理后的可用性、历史查询范围、上下文恢复入口及反馈在中断后的可达性 |
| A 已报告 ready 或形成 PR → 助手说明实际交付状态和仍需人工处理的事项 → 必要项目结论维护到原资产归属；用户继续讨论 B，或本轮结束 | 已明确：ready、工单结束、PR 合并及整体目标完成不能混同；结束讨论不必等待所有并行工作结束。原始记录与项目资产不自动成为助手长期记忆 | 查询与呈现真实交付状态；结果处理和必要资产更新的衔接，沿用既定文档分工 |

**收尾结论：**在能力和责任层，已确认方向能够覆盖“讨论 → 工具交接 → 执行反馈 → 用户决定或结果理解 → 必要沉淀与恢复”的最小闭环。本次推演未发现必须新增助手职责、另设业务实体或重新开启多对话设计的缺口；前提是已列出的查询、定向操作、来源关联和反馈能力在后续实现中成立。这是概念覆盖结论，不是接口或运行可靠性验证。

本轮讨论至此收尾。高重要性的交接与反馈回程，以及上下文接续仍是后续设计与验证重点，要求由 design-focus.md 维护。其余未决项保留在下表；只有用户另行启动实现设计时继续，不以本次走查作为代码实施授权。
